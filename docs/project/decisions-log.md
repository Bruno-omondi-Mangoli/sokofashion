D017: Seller payment methods at launch are M-Pesa Buy Goods Till, Paybill, Pochi la Biashara, and cash. All M-Pesa methods use buyer submitted codes confirmed by the seller, with duplicate code detection. Reason: these are the methods the pilot shops use today. Status: active, confirm Pochi la Biashara details in Phase 6.
D018: All five pilot shops have one staff member each, so staff roles and invitations are built early, in Phase 3, and the anti-theft module stays the main Pro feature. Reason: confirmed by the owner. Status: active.
D019: Roles are a fixed enum (owner, manager, attendant), not a separate table. Shops are created only through the create_shop function, and shop_members cannot be changed through the public API until controlled staff functions exist. Reason: simpler and safer, and it blocks self-assigned roles. Status: active.

D020: Database security is tested with pgTAP files in supabase/tests/database. Every shop-owned table must ship with isolation tests, and guardrail tests fail if a public table lacks Row Level Security or a security definer function lacks a fixed search_path. Reason: tenant isolation is non-negotiable and must not depend on memory. Status: active.
D021: GitHub Actions runs the database security tests as a separate job named Database tests, alongside Checks. Both must be green before merging, and both will be required by branch protection at the pilot stage. Reason: security tests must not depend on memory, and building the database from empty on every run proves migrations are complete. Status: active.
D022: Staging is a free Supabase cloud project named sokofashion-staging, holding fake data only. The second free project slot is reserved for production, created before the pilot with real shops. Local Docker is the third environment. Reason: the free plan allows two projects and the budget rule is zero spend until the pilot ends. Status: active.
D023: Database changes reach staging by running npx supabase db push from the laptop after the pull request is merged and both CI checks are green, using the dry run first. Automating this in CI is deferred. Reason: simplest safe workflow for a solo developer, and it avoids storing database credentials in GitHub for now. Status: active.
D024: Sellers and staff sign in with email and password at launch. Phone number login is deferred because it needs a paid SMS provider. Reason: zero spend until the pilot ends, and email login needs no extra service. Status: active, revisit after the pilot.
D025: Next.js Cache Components are switched off for now by using an empty Next.js config. Reason: they require extra wrapping around every page that reads cookies, which adds complexity without benefit at this stage. Status: active, revisit in Phase 11 if performance needs it.
D026: Sessions are managed with @supabase/ssr cookies and Server Actions. Pages that protect data check the user with supabase.auth.getUser on the server, and the proxy only refreshes sessions. Reason: the proxy alone is not a safe gatekeeper, and getUser is verified by the Supabase server. Status: active.
D027: A dedicated design system chunk (colour tokens, fonts, core components, restyle of existing pages) is scheduled at the start of Phase 4, before product screens are built. Screens before that are deliberately plain. Reason: design is easier to get right with real screens to style, and function comes first. Status: active.
D028: Reserved link names are blocked by a database constraint, and each user may create at most 3 shops, enforced inside create_shop with an advisory lock. Reason: link names become public addresses that must not clash with real pages or pose as the platform, and the rules must hold even when the form is bypassed. Status: active, stronger rate limiting comes in Chunk 15 and Phase 11.
D029: The app shows one generic message for taken and reserved link names and logs only error codes, not user data. Reason: avoids revealing the reserved list or which shops exist. Status: active.
D030: Staff are invited by email address and accept the invitation after logging in. No invitation emails are sent at launch. The owner tells the person by WhatsApp to sign up with that email. Reason: Supabase free email is heavily limited and custom email costs money (D013). Status: active, automatic invitation emails after the pilot.
D031: An invitation can only be accepted by a user whose email matches and is confirmed. Email confirmation must be switched on in staging and production before the pilot. Only owners may invite, deactivate or cancel, invitations are for manager or attendant only, and a shop may have at most 10 non-owner people including pending invitations. Reason: stops invitation theft and self promotion, and the limit will later come from plan limits. Status: active.
D032: Team members are deactivated with is_active false, never deleted, and owners can never be deactivated. All team changes go through database functions, because shop_members has no direct write access. Reason: keeps history, removes access instantly, and blocks self assigned roles. Status: active.
D033: A signed in person with no shop sees a choice screen (I own a shop, or I work in a shop and wait for an invitation) instead of the create shop form. Invitations are shown first when they exist. Reason: staff members must not be pushed to create shops. This is only a screen change, and the database still allows up to 3 shops per user. Status: active.

D034: Authentication settings on staging and production (confirm email, site URL, redirect URLs, email template) are set in the Supabase dashboard and recorded in a checklist in docs/environments.md. The local config.toml is not pushed to cloud projects. Reason: pushing local config would overwrite the cloud site address, and these settings are few. Status: active.
D035: Email confirmation links go to /auth/confirm with a one-time token hash, and the destination after confirming comes from a fixed allowed list. Local development has confirmation switched on with a fake inbox, so it behaves like staging. Reason: tests the real flow on the laptop and blocks open redirects. Status: active.
D036: The built-in Supabase email sender only delivers to organization team members and has a very low limit, so real sellers cannot sign up through it. Before the pilot, either buy a domain (about 12 dollars a year, also needed for shop links) and use a free tier email service with custom SMTP, or create the pilot accounts by hand in the dashboard. Reason: email confirmation protects invitations (D031) and needs real email delivery. Status: open, decide in Phase 12, recommendation is the domain.
D037: Password reset uses the same /auth/confirm route with type recovery. Recovery links always lead to /reset-password regardless of the next parameter, the forgot password form gives the same answer whether or not the email has an account, and a successful reset signs out all other sessions. Reason: avoids open redirects and account enumeration, and limits damage from a stolen session. Status: active.
D038: Every password box uses a shared PasswordField component with a Show and Hide button. Reason: seller phones have small keyboards and hidden typing causes failed logins. Status: active.

D039: The interface must be creative and distinctive. The identity is built from the parts of a kanga cloth: a woven border band (pindo) as the one bold element, a calm centre field, and a short Swahili saying (ujumbe) on quiet moments. Colours are indigo, marigold, hibiscus and teal on paper and sand, not cream and terracotta. Fonts are Young Serif for display and Atkinson Hyperlegible Next for body. Dark mode is deferred to Phase 11. Reason: owner requirement for a unique look, with legibility first for low end phones. Status: active.
D040: All colours, fonts and sizes are design tokens in src/app/globals.css. Every text and background pair is checked by an automated WCAG contrast test, and a live style guide at /design is hidden in production. Reason: accessibility must not depend on memory, and screens should be built from the same parts. Status: active.
D041: Swahili text in the interface must be confirmed by a native Swahili speaker before the pilot. Reason: wrong translations damage trust. Status: open, before Phase 12.
D042: next.config.ts must always keep the Tailwind loader rule for @tailwindcss/turbopack, and a unit test checks for it. Reason: the rule was deleted by mistake in Chunk 12, which silently removed all styling. Status: active.
